# ADR-008 — The relying-party flow for v1; OpenID conformance testing and certification are not now

**Status:** Accepted (2026-11-13, after a point-by-point review with the owner). Completes
[ADR-005](005-account-sessions-and-rp-tokens.md) §2.

## Context

[ADR-005](005-account-sessions-and-rp-tokens.md) §2 (Authorization Code flow for relying
parties) is accepted and not implemented: brig·id issues no token today.

Two questions came with implementing it. Should the OpenID Foundation's conformance suite
run in CI, and should brig·id be certified? And which of the choices ADR-005 left open, or
that the suite would force, does v1 make?

The suite was read to answer the first (its source, `OIDCCBasicTestPlan` and
`OIDCCCheckDiscEndpointIdTokenSigningAlgValuesSupported`). To pass its Basic OP and Config
OP plans a provider must sign with RS256, accept requests without PKCE, and serve a UserInfo
endpoint. Each of the three goes against a choice brig·id made on purpose.

## Decision

### 1. No conformance suite in CI and no certification for v1

Neither is a goal of v1, and certification is not planned. **One roadmap item, after v1**,
re-examines both. Until then brig·id says that it implements the OpenID Connect
Authorization Code flow, and never "conformant" or "certified".

What v1 has instead: end-to-end tests in which a demonstration relying party, written with
an ordinary OpenID Connect library, signs a person in through a real passkey ceremony.

### 2. Choices for the flow

| Point | Decision |
| --- | --- |
| Signature of ID tokens | **EdDSA (Ed25519) by default; no RSA key.** A composite post-quantum signature on request, at step 3 ([ADR-025](025-server-surface.md) §2). This departs from OpenID Connect Core §15.1, which makes RS256 mandatory: a site whose library cannot verify EdDSA cannot use brig·id |
| Kinds of clients | **Confidential and public.** A confidential client has a secret (256 bits generated by the server, shown once, stored hashed; `client_secret_basic` and `client_secret_post`). A public client has none |
| PKCE | **`S256` mandatory for every client**, as ADR-005 §2 says. `plain` is never accepted. Reopened only if a real application cannot do it |
| UserInfo endpoint | **Not in v1.** Added at the first real need |
| What a site receives | **The identifier only**: `sub`, the VSID of the chosen identity for that site. An identity's name and icon are labels inside brig·id; no site ever receives them. Information about the person that a site may ask for is the subject of [ADR-022](022-identity-attributes-and-consent.md) |
| Scopes | `openid` only |

Two details that follow:

- The token response carries an `access_token`, because OAuth 2.0 requires the field and
  libraries refuse a response without it. In v1 it is a random value that no endpoint
  accepts.
- `state` and `nonce` are honoured, `prompt=login` forces a new passkey ceremony,
  `prompt=none` answers without interface or with the standard error, `max_age` is compared
  with `auth_time`, and unknown parameters are ignored, as OpenID Connect Core asks.

### 3. Kept for the later item

Facts gathered on 2026-11-13, so that the work does not start from nothing:

- The suite is free software (MIT) and runs locally in containers. Its Basic OP plan uses
  clients with a secret, sends most requests without `code_challenge`, and tests UserInfo
  (GET, POST with header, POST with body); its discovery check fails with "RS256 support is
  required" when `id_token_signing_alg_values_supported` lacks `RS256`.
- Certification is self-declared on the Foundation's hosted suite. Fee: USD 700 for members,
  USD 3,500 otherwise, per deployment and calendar year. A waiver exists for free-software
  projects whose maintainers are not paid for it, on request, for members.

## Consequences

- `core`: ADR-005 §2 is implemented with the choices of §2 above.
- A demonstration relying party gets its own repository and serves as the target of the
  end-to-end tests.
- Some applications will not connect to brig·id in v1: those that need RS256, a UserInfo
  call, or an e-mail address. This is accepted and listed in the documentation.
- `protocol.md` §5 and §6 are updated with the implementation.
